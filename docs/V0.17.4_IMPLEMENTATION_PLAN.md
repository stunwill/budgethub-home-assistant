# Fynvo v0.17.4 Corrective Release

This corrective release is based on the mobile review performed on 20 August 2026.

## Scope

1. Add readable X and Y axis markings to the cash-flow forecast chart. X axis labels should show dates across the selected horizon. Y axis labels should show representative AUD balances including zero where it falls within the plotted range.
2. Remove the current `income_vs_expected` warning behaviour that compares imported income transactions with scheduled monthly income. Planned income is authoritative for forecasting and should be assumed unless the user explicitly marks or changes it. Imported transactions can still be used for reconciliation and reporting, but the absence of a matching transaction must not generate a warning.
3. Improve dashboard date-range responsiveness. Changing the date range should update the dashboard's command-centre data immediately without blocking on unrelated page data, financial-health, insights, imports, reconciliation, budgets or other background requests. Avoid duplicate full-data refreshes and stale responses overwriting newer selections.
4. Make success banners transient. Messages such as `Income updated.` should automatically clear after a short period and should also clear when navigating to a different page.
5. Simplify the category taxonomy. Consolidate obvious duplicates and near-duplicates, including combining house maintenance and house improvements under a single home-maintenance grouping. Preserve existing assigned data through aliases/mapping rather than deleting category history.
6. Redesign the Categories page around parent categories. Parent rows display totals aggregated from their children, plus direct-parent assignments where they exist.
7. Parent category rows include a clear disclosure/accordion control. Expanding a parent displays its children.
8. Parent and child category rows are selectable. Selecting a row opens the category modal in view mode with an Edit action.
9. Expanded child rows display each child's value for the selected date range.
10. Parent and child category rows display the number of matching entries/expenses.
11. Entry counts are active links. Activating the count opens a filtered list of matching records for that category, including descendant records when invoked from a parent.
12. Make the global date range meaningful on Recurring Expenses. Add a summary showing the total scheduled recurring-expense value falling within the selected date range. The list itself remains the source-record list unless filtered separately.
13. Add a frequency filter to Recurring Expenses with All, Weekly, Fortnightly, Every 4 Weeks / 28 Days, Monthly, Quarterly, Annual/Yearly, Custom and One-off options as applicable to the stored data.
14. Fix Categories values so category rows never display `Loading…` as a substitute for a missing monetary field. Category values must be calculated from matching financial records.
15. Change Recurring Expense Category from free text to a hierarchical dropdown. Parent categories are visually prominent and children are indented beneath their parent. Do not allow inactive categories to be newly assigned.

## Data and API requirements

- Add a category-summary API or extend `/api/categories` with optional `start` and `end` parameters. It must return, for each category: direct value, descendant-inclusive total value, direct entry count, descendant-inclusive entry count, child count and parent relationship.
- Category aggregation should include expense transactions plus relevant scheduled expense records (recurring expenses, bills and planned spending) where the category matches. The implementation must avoid double counting a record.
- Add a category-records endpoint or equivalent query parameters so the UI can retrieve the records behind an entry count.
- Recurring-expense range totals should be derived by expanding each active recurring record's schedule over the selected date window rather than multiplying a monthly equivalent blindly.
- Category consolidation must use an explicit migration/mapping table or idempotent migration routine so current user data remains valid.

## Performance requirements

- Dashboard date-range changes should not call the full `loadData()` path.
- Introduce a dedicated dashboard refresh function for range-dependent dashboard data.
- Use a request sequence/AbortController so a slower response for an older range cannot overwrite a newer range selection.
- Keep static/reference lists such as categories and accounts cached in component state unless the user edits them.
- Do not refresh Insights and Financial Health merely because the dashboard date range changed unless the current page actually needs those values.

## Acceptance criteria

- The chart visibly shows date and AUD balance markings on mobile and desktop.
- No current Insight tells the user income is missing merely because no actual bank transaction has been recorded.
- Changing the dashboard date range updates visible KPI values materially faster than v0.17.3 and does not wait for unrelated APIs.
- Success banners disappear automatically and do not persist across unrelated page navigation.
- Categories display as expandable parent groups with totals, child totals, entry counts, drill-through and edit/view modal behaviour.
- Recurring Expenses displays a date-range total and supports frequency filtering.
- Recurring Expense Category uses the hierarchical category selector.
- No category row shows `Loading…` as its amount.
